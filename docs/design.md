# Design

kanban is a board of the Claude Code sessions running on one Mac. Each card is a live session; cards are linked when one session spawned or forked another or ran it as a subagent, and messages between them are drawn on the board. Clicking a card opens its conversation in a native agent view, with the real TUI one toggle away.

## Why build it

No existing tool covers the set (surveyed 2026-10-24):

| Tool                                                              | Gap                                                              |
| ----------------------------------------------------------------- | ---------------------------------------------------------------- |
| `claude agents` (agent view)                                      | TUI only, background sessions only, no graph or messages         |
| Remote Control / claude.ai/code                                   | Chat view, not the TUI; no board, graph or messages              |
| Vibe Kanban, Claude Squad, CCManager, Conductor, Nimbalyst, Happy | Only see sessions they launch; no relationship or message graph  |
| CloudCLI, claude-code-viewer, opcode, agentsview                  | Read transcripts; resume through the SDK instead of the live TUI |
| Hook-based observability dashboards                               | Only sessions with their hooks; no TUI                           |

kanban builds on Claude Code's own primitives instead: the session registry, background jobs, `claude attach`, and transcripts.

## Sources of truth

Everything about sessions is read from `~/.claude`; kanban keeps no database. It stores only what people put on the board, in `KANBAN_STATE` (default `~/.local/state/kanban`, or `~/.local/state/kanban-<port>` off the default port so dev servers never share the board's files), each written atomically: `layout.json`, where cards sit, with placements pruned a day after their node leaves the board (a card someone dragged or resized is pinned there; a card kanban placed keeps its spot only while its subagent grid still fits and its project's frame stays clear of other projects' frames and of regions drawn for other directories, and otherwise moves to the nearest free space; inside a region of its own directory it holds any clear spot, and the region makes room instead); `annotations.json`, the board's sticky notes and stickers; `colours.json`, the colours people chose for project regions, keyed by cwd, validated against the palette, at most 200; `regions.json`, the project regions people drew, at most 100; and `comments.json`, the board agent's comment threads (where each is pinned, its messages, the agent's actions and replies, and the id of its headless Claude Code conversation), at most 200 threads of 200 events each. Beside those it keeps `usage.json`, a week of Claude usage samples for the top bar's chart.

| Need                                    | Source                                                                                       |
| --------------------------------------- | -------------------------------------------------------------------------------------------- |
| Live sessions                           | `~/.claude/sessions/<pid>.json` (watched)                                                    |
| Background jobs, including stopped ones | `~/.claude/jobs/<short>/state.json`                                                          |
| What a background session is doing      | `state.json` `detail`, `needs`, `state`                                                      |
| What an interactive session is doing    | last `tool_use` in its transcript                                                            |
| Transcript path                         | `~/.claude/projects/<slug(cwd)>/<sessionId>.jsonl`, falling back to a glob on the id         |
| Subagents                               | `<transcript dir>/<sessionId>/subagents/**/agent-<id>.meta.json`                             |
| Spawned by `claude --bg`                | `backgrounded · <short>` in a parent's Bash tool result                                      |
| Forked by `/bg`                         | `continued-in` record in the parent transcript                                               |
| Messages                                | `SendMessage` tool results (`msg_id`) matched to recipients' `origin.kind == "peer"` records |
| Card goal                               | latest `ai-title` record, else the first line of the latest `last-prompt`, else job `intent` |
| Artifacts                               | `Artifact` publish results: the claude.ai `url` and `title` in `toolUseResult`               |
| Claude usage                            | `api.anthropic.com/api/oauth/usage` with Claude Code's sign-in, every 5 minutes              |

Secrets that are never read or served: `sessions/*.key`, `daemon/control.key`, roster `ptyAuth`/`rvAuth`, `respawnFlags`, `providerEnv`. Claude Code's OAuth access token (the `Claude Code-credentials` keychain item, else `~/.claude/.credentials.json`) is read only to ask the usage API and is never served, logged or refreshed; Claude Code keeps it fresh.

## Data model

`src/shared/types.ts` is imported by server and page alike. A `Board` is `sessions`, `subagents`, `links` and `messages`. Links and messages point at `NodeRef`s, so subagents and sessions are both nodes. The model is derived, never stored, and rebuilt incrementally as files change.

An `Annotation` is a note (`text`, a `color` from a fixed palette of six, and for a status report the `session` it is linked to) or a sticker (a vendored Twemoji id, optional `rotation`), each with board coordinates `x`, `y`, size `w`, `h` and stacking order `z`. The server validates every field strictly: finite coordinates, sizes between 24 and 2400, text up to 20000 characters (request bodies up to 128 KiB so the longest note fits however it escapes), a sticker id from `src/web/stickers/manifest.ts`, and at most 500 on the board. Note text is GitHub-flavoured markdown, parsed with `mdast-util-from-markdown` and the GFM extensions into a syntax tree that `src/web/markdown.ts` turns into Preact elements; nothing reaches `innerHTML`, raw HTML shows as literal text, links keep only `http`, `https` and `mailto` URLs and open in a new tab with `rel="noopener noreferrer"`, and images show as links to their source so nothing loads until clicked. A note of nothing but paragraphs stays a big centred sticky; anything else reads as a left-aligned document that scrolls inside the note.

`Activity` folds Claude Code's `status` (busy, idle, waiting, shell) and job `state` (working, blocked, done, failed, stopped), plus whether the session has a live subagent, background shell or workflow, into seven states, each a colour paired with a shape:

| Activity  | Shape       | Meaning                                       |
| --------- | ----------- | --------------------------------------------- |
| working   | pulsing dot | mid-turn                                      |
| needs-you | triangle    | blocked on a person                           |
| watching  | eye         | turn ended, subagents or shells still running |
| idle      | ring        | waiting for a prompt                          |
| done      | check       | background job finished                       |
| failed    | cross       | background job failed                         |
| stopped   | square      | process gone, can be reattached               |

The states that ask something of a person stand out across the board at any zoom (`src/web/attention.css`). A card that needs you has an amber edge, a slowly breathing glow and a Needs you ribbon on its header, brighter on hover. Done has a green edge and a check that reads Finished · <time> on hover, failed a red edge; each plays a one-shot settle or shake only when the page sees a card move into that state, never on first sight. Idle has a slate-blue edge and a ring that reads Idle · <time> on hover; stopped keeps a dashed grey edge. Watching keeps the working card's accent edge and badge without the sweep, so it reads as busy off the main thread rather than waiting for you. Idle and done cards lift on hover, and a working card has a light sweeping along its top edge. Edges, glows and ribbons grow as the board zooms out so they keep their size on screen, and below 45% the ribbon shrinks to its icon. Subagent cards get the same treatment for working, idle and done. A session still waiting on subagents (launched and not yet returned, whether running or stalled) carries a second ribbon on its top-left edge, "3 running · 5 waiting", with the working sweep while any run and a dashed slate edge when all have stalled, shrinking to the waiting count when zoomed out; the top bar's subagent pill leads with the same running and waiting-on totals, and a project label counts its members' outstanding subagents beside its needs-you count. These counts cover every subagent from the last 30 minutes, nested and in workflows, not only the 40 cards a session shows, plus any older subagent with a descendant in that window (a parent blocked on a long nested call writes nothing while it waits). The board also sends the state of every outstanding subagent and the subagents of each workflow run, so the agent view can badge them beyond the cards. An agent team teammate is a peer, not something its session blocks on: it counts as running while it works and as returned once it ends its turn. A subagent has returned once its parent saw its result or task notification, its workflow journal records a result, the parent stopped it or the workflow run it belongs to (TaskStop or a notification), or its session's process is gone. A project frame with a member that needs you takes an amber edge and a count on its label, and the label grows with the zoom like the ribbons. Under reduced motion nothing pulses or moves; the emphasis stays static.

A session that published Artifacts shows its two newest as links along the bottom of its card, above the footer, with a count of the rest that opens the session; the session's header in the agent view lists them all. Each opens the artifact on claude.ai in a new tab, since claude.ai refuses to be framed. Only publishes count, a republish moves an artifact to the front, and only `https://claude.ai/artifact/…` and `/code/artifact/…` links are kept. Subagents' artifacts are not collected.

The top bar shows the account's Claude usage, read from the same usage API Claude Code's `/usage` calls rather than from any status line: the 5-hour session and weekly percentages beside a sparkline of the week, with a warning icon from 75% and a red edge from 90%. Clicking it opens a popover with both windows, when each resets, and a 7-day chart of both with a hover readout; the line breaks where the server was not sampling. A failed check keeps the last reading and history and says why (signed out, expired sign-in, rate limited, unreachable).

## Front end and back end

One Node 24 process on `127.0.0.1:7420` serves the built page and these endpoints:

| Endpoint                                                                  | Purpose                                                                                                                                                                                                                 |
| ------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /`                                                                   | the page                                                                                                                                                                                                                |
| `WS /api/feed`                                                            | `BoardFeed` frames: `layout`, `annotations`, `colours`, `regions`, `comments`, `usage` then a full `board` on connect, each again on change, `exit` and `report` outcomes, and one `comment` thread whenever it changes |
| `GET /api/sessions/:id/transcript`                                        | recent `TranscriptEntry`s; nothing on the page calls it any more                                                                                                                                                        |
| `GET /api/sessions/:id/files?q=`                                          | `@` completions: up to 50 paths under the session's cwd matching `q`, see Agent view                                                                                                                                    |
| `GET /api/sessions/:id/commands`                                          | `/` completions: built-in commands plus user and project commands and skills, names and descriptions only                                                                                                               |
| `POST /api/sessions`                                                      | `NewSessionRequest` → `claude --bg`; without `name` Claude Code names it, with `at` the card spawns there                                                                                                               |
| `POST /api/folder-picker`                                                 | `FolderPick`: opens a macOS choose-folder panel on the Mac running the server and answers with the chosen path, or `cancelled`                                                                                          |
| `POST /api/sessions/:id/exit`                                             | `ExitRequest` → 202 at once; the `ExitResult` arrives later as an `exit` feed frame, since asking can outlast the tunnel's ~100s limit                                                                                  |
| `POST /api/sessions/:id/report`                                           | → 202 at once; asks the session for a status report and writes the answer to a note beside its card, then sends a `ReportResult` as a `report` feed frame; 409 while one is already being asked                         |
| `PUT /api/layout`                                                         | `LayoutUpdate` → 204: stores one node's placement and broadcasts the layout                                                                                                                                             |
| `PUT /api/annotations/:id`                                                | `Annotation` → 204: creates or replaces one note or sticker and broadcasts the annotations                                                                                                                              |
| `DELETE /api/annotations/:id`                                             | 204: removes one note or sticker and broadcasts the annotations                                                                                                                                                         |
| `PUT /api/colours`                                                        | `RegionColourUpdate` → 204: sets one cwd's region colour, or `null` to return it to its default, and broadcasts the colours                                                                                             |
| `POST /api/regions`                                                       | `RegionDraft` → 201 `Region`: cwd must be an existing absolute directory, bounds finite and 96–20000 wide and tall; 409 at the cap                                                                                      |
| `PATCH /api/regions/:id`                                                  | `RegionPatch` → 200 `Region`: a new name (empty clears it) and/or all of x, y, w and h                                                                                                                                  |
| `DELETE /api/regions/:id`                                                 | → 204: removes the region and leaves its cards where they are                                                                                                                                                           |
| `POST /api/comments`                                                      | `CommentDraft` (x, y, text) → 201 `CommentThread`: pins a thread there and starts the board agent on the text; 409 at the cap                                                                                           |
| `POST /api/comments/:id/messages`                                         | `{text}` → 202: continues the thread's agent conversation; 409 while it is still running                                                                                                                                |
| `POST /api/comments/:id/cancel`                                           | → 204: stops the thread's running agent                                                                                                                                                                                 |
| `PATCH /api/comments/:id`                                                 | `CommentPatch` → 200: moves the pin (x and y together) and/or resolves or reopens the thread                                                                                                                            |
| `DELETE /api/comments/:id`                                                | → 204: stops its agent and removes the thread                                                                                                                                                                           |
| `POST /api/agent/tools/:tool`                                             | the board agent's MCP server only: runs one board tool for a live per-run token from loopback, see Ask the board                                                                                                        |
| `WS /api/attach/:short`                                                   | a `claude attach` pty: binary output down, `AttachClientFrame`s up                                                                                                                                                      |
| `WS /api/mirror/:sessionId`                                               | a cmux pane: `MirrorServerFrame`s (screen text on change, errors, end) down, `MirrorClientFrame`s (text, allowlisted keys) up                                                                                           |
| `WS /api/sessions/:id/conversation`, `WS /api/subagents/:id/conversation` | the agent view: `ConversationServerFrame`s down, `ConversationClientFrame`s up; `?since=<epoch>:<rev>` resumes                                                                                                          |
| `GET /healthz`                                                            | liveness                                                                                                                                                                                                                |

One attach per session: a second attach takes over and the first gets `taken-over`, because Claude Code redraws a shared session at the last attacher's size. Closing the socket kills the attach process, which detaches without stopping the session. If the attach drops into Claude's agent view (← on an empty prompt, recognised by its `claude agents` window title), kanban sends Enter to return, and Escape for a workspace trust dialog there. This guard is a convenience against stray keys, not a security boundary: whoever passes Cloudflare Access can already drive any background session, so Access is the boundary.

Interactive sessions in cmux panes are driven through the `cmux` CLI (`CMUX_BIN`), never Remote Control. Every 5s, and whenever the board changes, `cmux top --all --processes --format tsv` maps each process to its surface by walking process rows up to a surface row; a session whose registry pid maps to a surface is marked `cmux` on the board. A failed listing, or one with no process rows, keeps the last good surfaces for up to a minute instead of marking every cmux session read-only, and a send's own re-resolve never replaces the board's map. No other process's environment is read. Opening a mirror, every 5s while it is open, and every send re-resolve the surface: the registry entry must still be that session's live process (the same check as exit) and `cmux top` must still place that pid in a surface. While a client is connected, `cmux read-screen` polls the pane every 500ms and sends the text only when it changes. Text goes through `cmux paste` (with `--submit` for Enter), capped at 16,000 characters, so cmux refuses to paste over a draft someone is typing; keys go through `cmux send-key --force` from an allowlist (Enter, Escape, Tab, Shift+Tab, ↑, ↓, Backspace, Ctrl+C), because each is a deliberate keystroke and cmux would otherwise refuse every key while a question, permission prompt or picker is open, leaving no way to answer it. cmux's draft and dialog refusals are shown in plain words rather than as the CLI's hint to pass `--force`. ← and → are left out so the mirror stays inside its own session: ← on an empty prompt would open Claude's agent view, which lists and drives every session on the machine. The mirror sits behind the same origin check and authentication as attach, and that is the boundary. Every call uses `execFile` with an argument array and always names the workspace and surface, and the child loses `CMUX_WORKSPACE_ID`/`CMUX_SURFACE_ID`/`CMUX_PANEL_ID`/`CMUX_TAB_ID` so a missing flag can never fall back to the server's own pane. cmux only admits processes started inside cmux unless its socket is in password mode (`CMUX_SOCKET_PASSWORD`), so a launchd server is refused: the refusal is logged and shown in the mirror, and those sessions stay read-only. Mirror opens and every send are audited, with the key or the text length, never the text.

The server calls the first `claude` on `PATH` at startup (or `CLAUDE_BIN`), skipping cmux's shim, so `--bg` sessions resume as themselves.

Exiting asks the agent itself without touching the real session: `claude -p --resume <id> --fork-session --session-id <fork> --no-session-persistence --tools "" --strict-mcp-config --permission-mode dontAsk --settings '{"disableAllHooks":true}' --output-format json --json-schema {ready, reason}` answers from a throwaway fork that loads no MCP servers or hooks, cannot run tools, and leaves no transcript. The fork registers in `~/.claude/sessions` while it runs, so ingest ignores its id. A ready (or forced) background session gets `claude stop` then `claude rm`, never with `--discard-unpushed` or `--force-remove-worktree`, so `rm` refusing leaves it stopped and says why. An interactive session gets SIGTERM, only while its pid is still that session's live registry entry and `ps` shows a claude process that started when the entry did, so a reused pid is never signalled. Every exit is audited.

Status reports ask the same throwaway fork as the exit check (`askArgs` with a status prompt), so the session is not disturbed. The answer, headed with the time, goes into the session's earlier report note if one is still on the board (keeping where it was moved, its colour and stacking), otherwise into a new blue note placed two grid steps to the right of the card. The note's `session` field draws a dashed tether from the note's edge to the card's frame for as long as both are on the board; a note dragged over its card hides the tether, and a duplicate is a plain note. A full board refuses before asking, and an answer whose card left the board meanwhile is dropped with an error. One report per session at a time, audited as `session-report`; a feed reconnect frees the ? buttons, since an answer from before a server restart never comes.

## Agent view

Opening a card shows the session's conversation drawn by the board itself, so it never depends on the size of the terminal the session runs in: a session in a quarter-width cmux pane still fills the window, and the whole history scrolls. The terminal (attach or mirror) stays one toggle away in the header.

`src/server/conversation.ts` folds transcript records into `ConversationItem`s (`src/shared/conversation.ts`): typed prompts with image counts, slash and `!` commands with their output, assistant text, thinking (Claude Code writes it redacted, so usually just its duration), tool calls paired with their results (text capped at 12k characters, errors, image counts, edit patches, a subagent's id, a question's answers), compaction boundaries with their summary, interruptions, notices (`informational`, `api_error`), peer messages, task notifications and prompts typed while the session was working (`queued_command` attachments from a person). Hook, prompt-snapshot, environment and other attachments are never sent to the page. A typed prompt whose parent record already has an earlier prompt (an Esc Esc rewind or an edit) replaces that earlier branch: its items become `rewound` and are not drawn, as the TUI shows only the active chain. A background launch (`async_launched` Workflow or Agent results, `backgroundTaskId` Bash results) carries its task id and stays running until a task notification names its tool use or task id, or TaskStop stops it. It also tracks the model, cwd, branch, permission mode (`permission-mode` records), context tokens (input plus cache plus output of the last reply), output tokens, when the current turn started and which tool calls have no result yet. Each item has an index and a revision; a log keeps a random epoch so a reconnect with `since` gets only what changed, and a different epoch (the server restarted or the file was rewritten) gets a fresh window. The socket sends the newest 150 items, then changes as the file grows (polled every 400ms while someone watches); `more` pages 150 older ones, and the page loads them as you scroll up, keeping its place, with a Jump to latest pill while you are away from the bottom. Tool calls are compact lines that expand to their input and result: Bash shows the command, output and exit code, Edit, MultiEdit and Write a unified diff, Read the path and range, Grep and Glob the match count, Agent its prompt, result and a link to its subagent's view, with the subagent's own Working, Idle or Done badge in place of the call's mark once the board knows it, so a background launch that returned at once still reads as running or waiting like its card, TodoWrite a checklist, AskUserQuestion the answers, Artifact a link to the published page, MCP tools their input and result. A Workflow shows its summary and task id instead of its script, with the running and waiting counts of its run's agents on its line and each agent's badge and link in its body. A background Bash or Workflow keeps a running mark until its task notification. A call the user rejected is one short Rejected line instead of Claude Code's rejection text.

The status bar shows the turn's elapsed time while working, model, cwd, branch, permission mode (kept while a dialog hides the TUI's footer), how many tool calls are still running in the background, context and output tokens. The header's status line and the cards' status lines read markdown as plain text. Subagent cards open the same view, read-only, on the subagent's own transcript; so does any terminal session outside cmux.

Input goes through the drivers the board already has, and only for input: `cmux paste --submit` and forced `cmux send-key` for a session in a cmux pane (re-resolved every few seconds with the same live-process check as the mirror), and for a background session a `claude attach` pty at a fixed 120x40, opened only when something is sent or the session is waiting on a prompt, rendered by `@xterm/headless` so its screen can be read, and released after 30 idle seconds or when nobody watches. While the session's Terminal view is open, the attach hub keeps a headless copy of that attach's screen and the agent view types through it instead, so the session is never redrawn at 120x40 under someone's terminal; opening or closing the Terminal view releases the view's own attach. Input queued when the last viewer leaves is dropped, never typed. Every background session someone has open in the agent view counts as attached, whether or not its pty is open, so the board agent's `send_prompt` leaves it alone. A live session with no transcript yet still opens, takes its first prompt, and picks the transcript up once it is written. The composer sends with Enter (Shift+Enter adds a line), recalls earlier prompts and commands with Up and Down at the edges, completes `/` commands and `@` files, interrupts with Esc or Stop, and cycles the permission mode with Shift+Tab, reading the mode back from the TUI's footer. Text typed while Claude works is sent at once (Claude Code queues it) and shown as queued until the transcript has it. Because a person is typing here, `/`, `!` and `#` are allowed; control characters (anything but newline and tab) and text over 16,000 characters are refused. Before every prompt and key the server reads the screen itself, not the board's lagging activity: nothing is typed while it shows a question, permission prompt or menu, and an attach send reads it again before pressing Enter. Esc is sent only while Claude works (the composer only sends it then) or to close a menu. A menu that is not a numbered prompt, such as Rewind, is recognised by its footer hint and shown as a dialog that names it, with Esc to close it and the terminal, so the composer can never type into it. A numbered list in the conversation above the TUI's input box is not mistaken for a prompt. The board agent's refusals in `prompts.ts` are unchanged. Every send is audited as `view-send` with its kind and length, never the text.

A session waits on a prompt when the board says it needs you and its transcript has a tool call without a result; a background job that is only blocked on its next instruction takes prompts. The server then reads the TUI's screen (cmux `read-screen`, or the headless attach) and offers a native form: AskUserQuestion with its options, descriptions, single or multiple choice and Other, from the tool's input; a permission prompt with the tool's input (the command, or the diff) and the TUI's own numbered choices as shown on screen. Answering drives the TUI with the keys it expects, worked out on Claude Code 2.1.292 against scratch sessions: the cursor moves with Up and Down (wrapping) and Enter picks; a multiple-choice row toggles with Enter and the Submit row moves on; Other is a row the answer is pasted into (forced, as the dialog refuses ordinary paste), which checks it; with more than one question a review step ends in Submit answers. Before every keystroke the server reads the screen and checks it shows the same question and choice, and after each move that the cursor landed; anything else stops with a message and leaves the prompt for the terminal. Success shows as the tool result arriving in the transcript. A permission answer is checked against a fresh screen, never a cached one: it must name the pending tool whose command (Bash) or file name (file tools) the prompt shows, so a repeated or late Yes cannot approve the next tool; while the prompt shows no pending tool's command it is not answerable. A prompt that is not a tool call shows the screen's own text above its choices. Wrapped choices in a narrow pane are joined, and choices clipped by a pane too small to list them all are marked, so the form offers the visible ones and says to widen the pane or use the terminal.

`@` completion lists the repository's tracked and untracked, not ignored, files (`git ls-files --cached --others --exclude-standard`), or walks the directory (skipping hidden directories and `node_modules`, 8 levels, 50,000 entries), cached for 10 seconds. It refuses a cwd inside `~/.claude`, through symlinks too, and drops any entry that resolves there, checked on the entries it returns. `/` completion reads only the first 4 KiB of each command or skill file for its name and description, and skips a project command or skill that resolves outside the project or into `~/.claude`.

Parity gaps: the panels that commands such as `/cost`, `/model` or `/config` open in the TUI are not drawn; the command runs and Esc closes the panel, but its content only shows in the terminal. Prompts that are not tool calls (folder trust, MCP approvals, plan approval) are offered only as a numbered list read from the screen, without context. Thinking text is redacted in current transcripts, so only its duration shows. Images are counted (as the TUI's [Image #N] placeholders), not shown as thumbnails: the page would need an endpoint serving image bytes out of transcripts, which is deferred. Text appears when Claude Code writes each message, not token by token. Prompt history is this session's own, not the TUI's history across sessions. Rewind, transcript mode and vim keys are not offered.

Known gaps after review, with reasons: hook output (stop_hook_summary, hook_success, hook_additional_context) and @-mention attachments (file reads, edited files, diagnostics) are still not drawn, since their shapes vary by hook and they are kept off the page with the other attachments; the TUI's background task list cannot stop a task from here, because stopping is a TaskStop the session itself must call; a foreground Agent call shows no live tool count or tokens, since its agent id arrives only with its result; teammates are not listed separately from subagents; workflow progress is shown as its agents' states, not the TUI's phase panel; a workflow agent with no card is labelled by its id; transcript updates still wait behind queued input, because ticks and input share one queue per session; Esc with queued prompts was not compared with the TUI; a menu opened from another terminal is only seen when the view reads the screen (while it sends or the session waits), though prompts are still refused against it; and the composer, question and permission forms on a cmux pane were exercised only through cmux's own refusals, since `cmux top` stopped listing processes during review. The guard for a permission prompt binds Bash and file tools by what the prompt shows; other tools are bound only by being the pending call.

## Ask the board

Pressing / anywhere on the board pins a comment at the pointer and hands its text to the board agent, a headless Claude Code run the server starts in `KANBAN_STATE/agent`:

`claude -p --output-format stream-json --verbose --session-id <thread session> --tools "" --strict-mcp-config --mcp-config <kanban> --allowedTools mcp__kanban --permission-mode dontAsk --settings '{"disableAllHooks":true}' --disable-slash-commands --append-system-prompt <board prompt> -- <text>`

A reply in the thread runs again with `--resume <thread session>`, so it is one conversation. Every built-in tool is removed, so the agent cannot run commands or read files (which keeps it away from the secrets under `~/.claude`); it has only the `kanban` MCP server, `src/agent/mcp.ts`, a stdio JSON-RPC server that validates each call against `src/agent/tools.ts` and forwards it to `POST /api/agent/tools/:tool`. The server validates it again and runs it against the same stores, launcher and exit flow the board uses. The stream-json output is folded into thread events: each tool call becomes a compact action line that turns into the tool's one-line summary ("Moved 6 cards", "Created note '## Report'"), and assistant text becomes replies. One run per thread, at most four at once, 15 minutes each; Stop kills it. Runs are excluded from the board like the exit fork: the thread's session id is chosen before the run starts and ingest ignores every id a thread owns. Runs work in `<state>/agent`, which holds a `.kanban-board-agent` marker, and ingest also ignores any session whose directory has that marker, so another kanban server on the Mac leaves them off its board too. Stopping the server stops its runs and notes it in their threads.

| Tool                                                             | Does                                                                                                                                                              |
| ---------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `board_snapshot`                                                 | sessions with card rectangles (the page's own placement code), activity and region; subagents; regions; notes; stickers; the comment's pin                        |
| `read_transcript`                                                | up to 80 recent transcript entries, each cut to 600 characters, 24k in all                                                                                        |
| `ask_session`                                                    | a free-form question answered from the exit check's throwaway `--fork-session` fork with no tools, so the session is not disturbed                                |
| `send_prompt`                                                    | types a prompt into a background session through a short-lived `claude attach` pty (bracketed paste, then Enter), or a cmux session through `cmux paste --submit` |
| `finish_session`                                                 | the board's non-forced exit: the session is asked first and only exits if it agrees                                                                               |
| `start_session`                                                  | `claude --bg` in a directory, optionally placed                                                                                                                   |
| `put_note`, `put_sticker`, `delete_annotations`, `find_stickers` | notes in markdown (a new one without `w` and `h` is sized to its text) and stickers by manifest id                                                                |
| `arrange`                                                        | moves and resizes many cards (pinned), regions and annotations in one all-or-nothing call                                                                         |
| `create_region`, `update_region`, `delete_region`                | project regions and their directory's colour                                                                                                                      |

Security. The agent acts with the user's reach on the board but no further: it cannot force an exit, run commands or read files. `send_prompt` refuses a session waiting on a question or permission prompt (typing would answer it), a background session someone has open on the board, and a terminal session outside cmux, and it refuses text whose first non-space character is `!`, `/` or `#` (the session would run it as a shell command, slash command or memory note without asking) or that holds control characters (which could end the bracketed paste early and type the rest raw); peer messaging was not used because its socket needs the session keys kanban never reads. Each run gets a random 256-bit token, passed to the run in its environment (the MCP server inherits it, so it never appears in a command line), stored only as a SHA-256 digest, revoked when the run ends and expiring with its 15-minute limit. `/api/agent/tools` accepts only that bearer token, only from a loopback socket, and refuses requests carrying Cloudflare's tunnel headers, since cloudflared also connects from loopback; browser credentials never open it, so it works the same with `KANBAN_AUTH=access`. Every tool call except the read-only snapshot, transcript and sticker search is audited as `board-agent` with the thread id, its target, the text it sent, asked or started a session with, and its outcome; exits and new sessions are also audited as usual with identity `board-agent`.

## User flows

1. **Scan.** Open the board. Cards group into families (a session and everything it spawned), newest first by when they started, so cards stay put while sessions work. Each card shows its name and what it is doing above its goal in large type, with a state badge. Dragging a card carries everything linked to it: its subagents, the sessions it spawned or forked (unless they sit in another project) and the notes tethered to it. Linked cards kanban placed stay unpinned. A dragged card steps aside rather than land in another project's frame, and a drag that ends where it began moves nothing else.
2. **Follow messages.** A message animates along a dashed arc from sender to recipient; the messages rail lists them newest first, and selecting one highlights both ends.
3. **Focus.** Click a card. It expands into the session's conversation with focus in the composer; type to send, and answer questions and permission prompts in place. Terminal in the header switches to the real TUI (an attach for a background session, the cmux mirror for a pane), Conversation switches back. Close returns to the board, and the session keeps running.
4. **Drive a cmux pane.** In the terminal view of a session in a cmux pane, a monospace mirror of the pane takes a prompt box (Enter sends, Shift+Enter adds a line; ↑, ↓ and Esc go straight through on an empty prompt) and buttons for the allowlisted keys. cmux refusals, such as a draft in the terminal's prompt, appear above the prompt.
5. **Read.** Any other interactive card (started in a terminal outside cmux), and every subagent card, opens its conversation read-only.
6. **Start.** New session: pick a folder from the recent projects, or from a macOS folder panel on the Mac, optionally name it, give a first prompt. It appears on the board and opens focused.
7. **Start in place.** Right-click the board (or press A) and type just the prompt. It starts in the group's project under the pointer, or the most recently active one (Tab cycles); a ghost card holds the spot until the session lands there.
8. **Draw a project region.** Right-click the board and pick New project region here, press R, or use the region button by the zoom controls. Pick a directory (recent ones suggested) and optionally a name. The region is a dashed frame that moves by dragging its label and resizes from any edge or corner, snapping to the grid. Sessions under its directory whose card centre lies inside belong to it, as do cards dropped there; the frame grows to hold them, and a project group touching it is adopted so one frame shows. A new region lands in the nearest spot clear of other project frames. Moving the region carries its cards, which then stay where they were put, everything linked to them and the notes and stickers centred inside its frame, and it steps aside rather than land on another project. Resizing starts from the region's drawn rectangle, not the frame grown around its cards, and an edge stops short of a neighbouring project. The directory is stored resolved, so a path through a symlink still claims its sessions. The quick prompt over a region starts the session in its directory and places the card inside; when the region is full the card goes just below it and the region grows to hold it. When a project's frame grows into another, as its cards gain subagents or new cards arrive, the other project steps right or down out of the way with its cards, notes and stickers, and so on down the board; the page does this shortly after the frames meet, never during a drag or while a quick prompt is open.
9. **Move, colour, rename or delete a project.** Drag any project label, drawn or grouped, to move the project with its cards, what is linked to them and the notes and stickers centred in its frame; it steps aside rather than land on another project. Click a project label without dragging, or right-click it, for its menu: one of eight colours (arrow keys move between swatches), and for a drawn region Rename, Exit every session (asking first, as its close button does) and Delete region; deleting leaves the cards alone. Right-clicking anywhere inside a drawn region opens the same menu topped with New session here, Add note here and Add sticker here. Escape or a click elsewhere closes it. Clicking a project's frame, or opening its menu, brings that frame in front of the frames it overlaps until another is brought forward, so a covered label or close button can be reached. A colour applies at once and sticks to the project's directory, so every frame for that cwd, drawn or grouped, shares it.
10. **Exit.** Hover a card and click its corner ×, then confirm. The agent is asked whether it is safe to exit: if so the card leaves, otherwise it shakes and shows why. Hold Shift for a red × that force-exits without asking, and Option (Alt) to skip the confirm dialog.
11. **Ask for a status report.** Hover a card and click the ? beside its ×. The button spins while the agent is asked; its answer lands in a note next to the card, tied to it by a dashed line, and asking again rewrites that note. If the agent cannot answer, the card shows why.
12. **Answer what needs you.** When any session needs you, the top bar shows how many with a button that pans to the next one (J does the same outside text fields), top to bottom then left to right, wrapping around; the card pulses once and takes focus, so Enter opens it.
13. **Annotate.** Press N (or right-click → Add note here, or the note button by the zoom controls) for a sticky note at the pointer, already in edit mode; Escape or clicking away saves it. Press S for the sticker picker: type to filter, arrows to choose, Enter to place. Drag to move, drag the corner to resize (stickers keep their shape), double-click or Enter to edit a note's markdown source; its rendering shows headings, lists, tables, code and links, and ticking a task-list checkbox rewrites `[ ]` to `[x]` in the source. A wheel over a note whose content overflows scrolls the note, not the board. Click selects, Shift+click adds to the selection, clicking the board clears it. Right-click a note or sticker for Edit text, Colour, Duplicate (⌘D), Bring to front (⌘]), Send to back (⌘[) and Delete (⌫); arrows nudge the selection a pixel, Shift+arrows a grid step. Notes and stickers sit above group frames and beneath cards, in board coordinates, so they pan and zoom with everything else.
14. **Ask the board.** Press / anywhere on the board (not while typing, in a terminal or a mirror) and type a request, such as "organise my board into projects" or "write a report of what acme-api did". Enter sends; a pin stays where you pressed, glowing while the agent works, and its thread shows your message, each action as it happens and the agent's reply. Reply in the thread to carry on the same conversation, Stop to cancel. Drag a pin to move it; click it to open or close its thread; right-click it for Open, Resolve or Reopen and Delete (⌫ on a focused pin). Resolved pins fade.

## Infrastructure

The host runs two launchd user agents:
- `kanban`: `node src/server/main.ts` from the checkout, with `~/.config/kanban/env` in its environment and a `PATH` that reaches `claude` (or `CLAUDE_BIN` set).
- `kanban-tunnel`: `cloudflared tunnel run` for the `kanban` tunnel.

A hostname such as `kanban.example.com` routes through the tunnel and is gated by Cloudflare Access on your Access team, allowing one identity. Defence in depth: cloudflared requires the Access token before proxying, the server verifies `Cf-Access-Jwt-Assertion` against the team's keys and audience, and WebSocket upgrades must come from the board's own origin. Local development runs with `KANBAN_AUTH=off`, which binds to localhost only.

`scripts/cloudflare-setup.ts` creates the tunnel, its DNS record and the Access application from an API token and the account, zone, hostname, Access team and allowed email it is given, idempotently, and writes the tunnel token and audience to `~/.config/kanban/`.

A web app instead of a desktop wrapper: the server must run as a long-lived local service anyway, and a PWA manifest makes it installable.

## Visual design

Flat and quiet: a warm off-white canvas, white cards with hairline borders, no shadows except on the focused card, one accent colour. Inter for the interface, JetBrains Mono for terminals, Lucide icons. Light and dark follow the system, with a toggle. State is always colour plus shape.

Project regions are tinted from an eight-colour palette (`src/web/regions.css`, `src/shared/colours.ts`): a faint fill, a stronger border and a label chip whose text keeps at least 4.5:1 contrast in both themes. Each cwd hashes to a stable default colour, so a project keeps its colour everywhere, though two neighbours can share one; a chosen colour overrides it.
