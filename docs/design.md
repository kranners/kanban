# Design

kanban is a board of the Claude Code sessions running on one Mac. Each card is a live session; cards are linked when one session spawned or forked another or ran it as a subagent, and messages between them are drawn on the board. Clicking a card opens its conversation in a native agent view, with the real TUI one toggle away.

## Why build it

No existing tool covers the set (surveyed 2026-10-24):

| Tool                                                              | Gap                                                              |
| ----------------------------------------------------------------- | ---------------------------------------------------------------- |
| `claude agents` (agent view)                                      | TUI only, background sessions only, no graph or messages         |
| Remote Control / claude.ai/code                                   | Chat view, not the TUI; no board, graph or messages              |
| Vibe Kanban, Claude Squad, CCManager, Conductor, Nimbalyst, Happy | Only see sessions they launch; no relationship or message graph  |
| CloudCLI, claude-code-viewer, opcode, agentsview                  | Read transcripts; resume through the SDK instead of the live TUI |
| Hook-based observability dashboards                               | Only sessions with their hooks; no TUI                           |

kanban builds on Claude Code's own primitives instead: the session registry, background jobs, `claude attach`, and transcripts.

## Sources of truth

Everything about sessions is read from `~/.claude`; kanban keeps no database. It stores only what people put on the board, in `KANBAN_STATE` (default `~/.local/state/kanban`, or `~/.local/state/kanban-<port>` off the default port so dev servers never share the board's files), each written atomically: `layout.json`, where cards sit, with placements pruned a day after their node leaves the board (a card someone dragged or resized is pinned there; a card kanban placed keeps its spot only while its subagent grid still fits and its project's frame stays clear of other projects' frames and of regions drawn for other directories, and otherwise moves to the nearest free space; inside a region of its own directory it holds any clear spot, and the region makes room instead); `annotations.json`, the board's sticky notes and stickers; `colours.json`, the colours people chose for project regions, keyed by cwd, validated against the palette, at most 200; `regions.json`, the project regions people drew, at most 100; `butler.json`, the sessions Butler watches, at most 100; and `comments.json`, the comment threads of the board agent and of Butler (where each is pinned, its messages, the agent's actions and replies, and the id of its headless Claude Code conversation; for Butler's, `to: "butler"`, what it was about, the messages spike has not collected yet and those it is still answering), at most 200 threads of 200 events each. Beside those it keeps `usage.json`, a week of Claude usage samples for the top bar's chart, `accounts.json`, a week of samples per cswap account keyed by email and organization, and `archive.json`, the cards and sessions whose work is over, for the sidebar's Archive.

| Need                                    | Source                                                                                       |
| --------------------------------------- | -------------------------------------------------------------------------------------------- |
| Live sessions                           | `~/.claude/sessions/<pid>.json` (watched)                                                    |
| Background jobs, including stopped ones | `~/.claude/jobs/<short>/state.json`                                                          |
| What a background session is doing      | `state.json` `detail`, `needs`, `state`                                                      |
| What an interactive session is doing    | last `tool_use` in its transcript                                                            |
| Transcript path                         | `~/.claude/projects/<slug(cwd)>/<sessionId>.jsonl`, falling back to a glob on the id         |
| Subagents                               | `<transcript dir>/<sessionId>/subagents/**/agent-<id>.meta.json`                             |
| Spawned by `claude --bg`                | `backgrounded · <short>` in a parent's Bash tool result                                      |
| Forked by `/bg`                         | `continued-in` record in the parent transcript                                               |
| Messages                                | `SendMessage` tool results (`msg_id`) matched to recipients' `origin.kind == "peer"` records |
| Messages to claude.ai sessions          | claude.ai remote-session `send_message` and `create_session` calls                           |
| Card goal                               | latest `ai-title` record, else the first line of the latest `last-prompt`, else job `intent` |
| Artifacts                               | `Artifact` publish results: the claude.ai `url` and `title` in `toolUseResult`               |
| Claude usage                            | `api.anthropic.com/api/oauth/usage` with Claude Code's sign-in, every 5 minutes              |
| Several accounts                        | `cswap list --json` (cswap's own cache) every minute; without cswap, the usage API above     |
| Sessions on another account             | the same files under every cswap profile, `<cswap root>/sessions/<n>-<email slug>/`          |

Secrets that are never read or served: `sessions/*.key`, `daemon/control.key`, roster `ptyAuth`/`rvAuth`, `respawnFlags`, `providerEnv`. Claude Code's OAuth access token (the `Claude Code-credentials` keychain item, else `~/.claude/.credentials.json`) is read only to ask the usage API and is never served, logged or refreshed; Claude Code keeps it fresh.

## Data model

`src/shared/types.ts` is imported by server and page alike. A `Board` is `sessions`, `subagents`, `links` and `messages`. Links and messages point at `NodeRef`s, so subagents and sessions are both nodes. The model is derived, never stored, and rebuilt incrementally as files change.

An `Annotation` is a note (`text`, a `color` from a fixed palette of six, for a status report the `session` it is linked to, and `author: "butler"` on one Butler wrote), one of Butler's cards (`kind: "butler-card"`, a `title`, one of five states, an optional `status` line, `summary`, https `link`, `selfFix` id and `watching` flag, and a `history` of up to 40 states with their time and status line, which the server appends to whenever Butler or spike changes the state or status), which moves like a session card: it snaps to the grid as it is dragged and resized within a session card's sizes, carries Butler's notes pinned beside it, zoomed in shows a session card's near view with its timeline, and belongs to the smallest project frame its centre is dropped in, which grows to hold it, edges it in the project's colour and carries it when the project moves, or a sticker (a vendored Twemoji id, optional `rotation`), each with board coordinates `x`, `y`, size `w`, `h` and stacking order `z`. The server validates every field strictly: finite coordinates, sizes between 24 and 2400, text up to 20000 characters (request bodies up to 128 KiB so the longest note fits however it escapes), a sticker id from `src/web/stickers/manifest.ts`, and at most 500 on the board. Note text is GitHub-flavoured markdown, parsed with `mdast-util-from-markdown` and the GFM extensions into a syntax tree that `src/web/markdown.ts` turns into Preact elements; nothing reaches `innerHTML`, raw HTML shows as literal text, links keep only `http`, `https` and `mailto` URLs and open in a new tab with `rel="noopener noreferrer"`, and images show as links to their source so nothing loads until clicked. A note of nothing but paragraphs stays a big centred sticky; anything else reads as a left-aligned document that scrolls inside the note.

`Activity` folds Claude Code's `status` (busy, idle, waiting, shell) and job `state` (working, blocked, done, failed, stopped), plus whether the session has a live subagent, background shell or workflow, into seven states, each a colour paired with a shape:

| Activity  | Shape       | Meaning                                       |
| --------- | ----------- | --------------------------------------------- |
| working   | pulsing dot | mid-turn                                      |
| needs-you | triangle    | blocked on a person                           |
| watching  | eye         | turn ended, subagents or shells still running |
| idle      | ring        | waiting for a prompt                          |
| done      | check       | background job finished                       |
| failed    | cross       | background job failed                         |
| stopped   | square      | process gone, can be reattached               |

The states that ask something of a person stand out across the board at any zoom (`src/web/attention.css`). A card that needs you has an amber edge, a slowly breathing glow and a Needs you ribbon on its header, brighter on hover. Done has a green edge and a check that reads Finished · <time> on hover, failed a red edge; each plays a one-shot settle or shake only when the page sees a card move into that state, never on first sight. Idle has a slate-blue edge and a ring that reads Idle · <time> on hover; stopped keeps a dashed grey edge. Watching keeps the working card's accent edge and badge without the sweep, so it reads as busy off the main thread rather than waiting for you. Idle and done cards lift on hover, and a working card has a light sweeping along its top edge. Edges, glows and ribbons grow as the board zooms out so they keep their size on screen, and below 45% the cards give way to project summaries. Subagent cards get the same treatment for working, idle and done. A session with subagents shows its four newest as chips along the bottom of its card body, and in the near view under its header, newest first: a state dot (accent and gently pulsing while working, slate while waiting, green and dimmed once returned), the subagent's description or else its type, clipped, and how long since it last moved, with "+N" for the rest of its recent subagents; a chip opens that subagent's conversation, or the session's own for a cloud session, whose subagents have no transcript here (`src/web/subagentChips.ts`). The separate subagent cards under the session stay as they were. A session's workflow runs sit above its goal as bars with the run's name, its agents finished and started from its journal, and "N agents" from the run's subagents; a run that ended stays for 30 minutes, filled green, reading "6 agents · done". The top bar's subagent pill leads with the same running and waiting-on totals, and a project label counts its members' outstanding subagents beside its needs-you count. These counts cover every subagent from the last 30 minutes, nested and in workflows, not only the 40 cards a session shows, plus any older subagent with a descendant in that window (a parent blocked on a long nested call writes nothing while it waits). The board also sends the state of every outstanding subagent and the subagents of each workflow run, so the agent view can badge them beyond the cards. A cloud session's subagents and workflow runs come from its mirrored transcript instead, since their own files never reach the board (`src/server/ingest/cloudAgents.ts`): each Agent or Task call is a subagent, running until its result, or for a background launch until its task notification, under the same 30 minute window and 40 card limit, and each Workflow call is a run with its name but no agent counts, which the mirror does not carry. Records a subagent writes into its parent's stream, marked by `parent_tool_use_id`, count toward the session's tokens and keep their call fresh but never become the session's doing or steps, and a runner leaves them out of its sessions' detail the same way. An agent team teammate is a peer, not something its session blocks on: it counts as running while it works and as returned once it ends its turn. A subagent has returned once its parent saw its result or task notification, its workflow journal records a result, the parent stopped it or the workflow run it belongs to (TaskStop or a notification), or its session's process is gone. A project frame with a member that needs you takes an amber edge and a count on its label, and far out its summary lists that session first with its question. Under reduced motion nothing pulses or moves; the emphasis stays static.

A doc store is a folder of docs that sessions write for each other. It is not on the canvas: `KANBAN_STATE/doc-stores.json` (`src/server/docStores.ts`) registers each `DocStore` (`id`, a `title` of 1 to 60 characters on one line, `createdAt`, and `updatedAt`, which moves on every rename and file write or delete), and every session may read and change every store. Its files live under `KANBAN_STATE/docs/<store>/<path>`, written to a temporary file and renamed, and indexed in memory as `DocFile`s (`path`, `size`, `updatedAt`). Paths are relative, `/`-separated, at most 8 segments and 240 characters, each segment starting with a letter, digit, `_` or `-` (so no dot files and no `..`), and end in `.md`, `.txt`, `.json`, `.csv`, `.svg`, `.png`, `.jpg`, `.jpeg`, `.gif` or `.webp` (`src/shared/docPaths.ts`). A file is at most 10 MiB (a text write at most 1 MiB), a store holds at most 1000 files and 100 MiB. Deleting a store deletes its folder. Boards from before the registry kept stores as a `docs` annotation kind linked to sessions by relations: at startup each such annotation becomes a registry entry with the same id and title, its relations are dropped, and a `docs/<id>` folder with files but no entry is registered as "Untitled docs". The migration runs again harmlessly on every start.

A `Relation` is a manual link the person draws between two ends, each a session (`RelationEnd`), stored in `KANBAN_STATE/relations.json`. A pair is unordered and unique, a cloud session can't be an end, and the board holds at most 500. Relations are separate from `Board.links`, which ingest derives and the layout treats as a family tree. A relation whose session has been off the board for a day is pruned.

A session that published Artifacts shows its two newest as links along the bottom of its card, above the footer, with a count of the rest that opens the session; the session's header in the agent view lists them all. Each opens the artifact on claude.ai in a new tab, since claude.ai refuses to be framed. Only publishes count, a republish moves an artifact to the front, and only `https://claude.ai/artifact/…` and `/code/artifact/…` links are kept. Subagents' artifacts are not collected.

The top bar shows the account's Claude usage, read from the same usage API Claude Code's `/usage` calls rather than from any status line: the 5-hour session and weekly percentages beside a sparkline of the week, with a warning icon from 75% and a red edge from 90%. Clicking it opens a popover with both windows, when each resets, and a 7-day chart of both with a hover readout; the line breaks where the server was not sampling. A failed check keeps the last reading and history and says why (signed out, expired sign-in, rate limited, unreachable). With [cswap](https://github.com/realiti4/claude-swap) managing several Claude logins, the pill shows the default account's windows, prefixed by its alias or number, and the popover lists every account with its 5-hour and weekly bars, resets and a weekly sparkline; **Make default** runs `cswap switch <n>`, which changes the `~/.claude` login every default session draws on. An account cswap can't read usage for says why and what to do: a login whose refresh token has lapsed (`relogin_required`) names the steps that fix it, `claude` then `/login` as that email, then `cswap add`, which refreshes the slot in place. Both new-session forms then offer an account picker: a non-default account launches through `cswap run <n> --share-history -- <claude args>`, so the session lives in that account's profile (its own registry, jobs and daemon) while its transcripts stay in `~/.claude/projects`. The board reads every profile beside `~/.claude`, marks a card with the account it runs on, and gives every per-session `claude` call (attach, stop, rm, the readiness and report forks) `CLAUDE_CONFIG_DIR` for that profile. Workspace trust lives in each profile, so a folder must be trusted once under `cswap run <n>` too.

One attach per session: a second attach takes over and the first gets `taken-over`, because Claude Code redraws a shared session at the last attacher's size. Closing the socket kills the attach process, which detaches without stopping the session. If the attach drops into Claude's agent view (← on an empty prompt, recognised by its `claude agents` window title), kanban sends Enter to return, and Escape for a workspace trust dialog there. This guard is a convenience against stray keys, not a security boundary: whoever passes Cloudflare Access can already drive any background session, so Access is the boundary.

Interactive sessions in cmux panes are driven through the `cmux` CLI (`CMUX_BIN`), never Remote Control. Every 5s, and whenever the board changes, `cmux top --all --processes --format tsv` maps each process to its surface by walking process rows up to a surface row; a session whose registry pid maps to a surface is marked `cmux` on the board. A failed listing, or one with no process rows, keeps the last good surfaces for up to a minute instead of marking every cmux session read-only, and a send's own re-resolve never replaces the board's map. No other process's environment is read. Opening a mirror, every 5s while it is open, and every send re-resolve the surface: the registry entry must still be that session's live process (the same check as exit) and `cmux top` must still place that pid in a surface. While a client is connected, `cmux read-screen` polls the pane every 500ms and sends the text only when it changes. Text goes through `cmux paste` (with `--submit` for Enter), capped at 16,000 characters, so cmux refuses to paste over a draft someone is typing; keys go through `cmux send-key --force` from an allowlist (Enter, Escape, Tab, Shift+Tab, ↑, ↓, Backspace, Ctrl+C), because each is a deliberate keystroke and cmux would otherwise refuse every key while a question, permission prompt or picker is open, leaving no way to answer it. cmux's draft and dialog refusals are shown in plain words rather than as the CLI's hint to pass `--force`. ← and → are left out so the mirror stays inside its own session: ← on an empty prompt would open Claude's agent view, which lists and drives every session on the machine. The mirror sits behind the same origin check and authentication as attach, and that is the boundary. Every call uses `execFile` with an argument array and always names the workspace and surface, and the child loses `CMUX_WORKSPACE_ID`/`CMUX_SURFACE_ID`/`CMUX_PANEL_ID`/`CMUX_TAB_ID` so a missing flag can never fall back to the server's own pane. cmux only admits processes started inside cmux unless its socket is in password mode (`CMUX_SOCKET_PASSWORD`), so a launchd server is refused: the refusal is logged and shown in the mirror, and those sessions stay read-only. Mirror opens and every send are audited, with the key or the text length, never the text.

The server calls the first `claude` on `PATH` at startup (or `CLAUDE_BIN`), skipping cmux's shim, so `--bg` sessions resume as themselves.

Exiting asks the agent itself without touching the real session: `claude -p --resume <id> --fork-session --session-id <fork> --no-session-persistence --tools "" --strict-mcp-config --permission-mode dontAsk --settings '{"disableAllHooks":true}' --output-format json --json-schema {ready, reason}` answers from a throwaway fork that loads no MCP servers or hooks, cannot run tools, and leaves no transcript. The fork registers in `~/.claude/sessions` while it runs, so ingest ignores its id. A ready (or forced) background session gets `claude stop` then `claude rm`, never with `--discard-unpushed` or `--force-remove-worktree`, so `rm` refusing leaves it stopped and says why. An interactive session gets SIGTERM, only while its pid is still that session's live registry entry and `ps` shows a claude process that started when the entry did, so a reused pid is never signalled. Every exit is audited.

Status reports ask the same throwaway fork as the exit check (`askArgs` with a status prompt), so the session is not disturbed. The answer, headed with the time, goes into the session's earlier report note if one is still on the board (keeping where it was moved, its colour and stacking), otherwise into a new blue note placed two grid steps to the right of the card. The note's `session` field draws a dashed tether from the note's edge to the card's frame for as long as both are on the board; a note dragged over its card hides the tether, and a duplicate is a plain note. A full board refuses before asking, and an answer whose card left the board meanwhile is dropped with an error. One report per session at a time, audited as `session-report`; a feed reconnect frees the ? buttons, since an answer from before a server restart never comes.

Digests are the passive summaries behind the far narrative and the near Progress section (`src/server/digests.ts`). They never ask a session anything: the server sends one project frame at a time (its sessions' goals, states, tasks, recent steps and the last ten user, assistant and peer turns of each transcript) to `claude -p --model haiku --no-session-persistence --tools "" --strict-mcp-config --permission-mode dontAsk --settings '{"disableAllHooks":true}' --setting-sources "" --disable-slash-commands --output-format json --json-schema … --system-prompt …`, which answers with a markdown narrative and, per session, what it is doing now, how far along it is and why it is stuck (empty when it is not). The run's working directory is `KANBAN_STATE/agent`, which carries the `.kanban-board-agent` marker, and nothing is saved, so digest runs never reach the board. Every 20 seconds, and only while a board page is connected, the server digests the frames whose fingerprint changed one after another, most in need first (needs-you or working first, then the most recently updated); the fingerprint hashes its sessions' states, doing, needs, goals, tasks and steps, not times or transcripts, so quiet frames cost nothing. A frame is digested at most every two minutes and one run happens at a time; a failure logs one line, keeps the previous digest and pauses digests for five minutes. Digests are cached in `KANBAN_STATE/digests.json`, keyed by frame, so a restart does not rerun them, and a frame that leaves the board is forgotten.

Region peers. Every session the board starts gets `--settings` with HTTP hooks on `UserPromptSubmit`, `SubagentStart` and `PostToolBatch`, all pointing at `POST /api/hooks/peers` (`src/server/peers.ts`). The server finds the project frame holding the session (a drawn region or a project group, the same units the digests use) and answers with its live frame-mates (those with a registry pid, so SendMessage reaches them): name, state, worktree, goal and digest `now` (or `doing`), and an instruction to coordinate through SendMessage. Only peers on the same account are listed, since another cswap profile has its own registry and SendMessage can't reach it; the board says so instead, with an amber link chip in the card's footer counting the live frame-mates on other accounts (its tooltip names them) and, zoomed in, a sentence under the goal (`src/web/reach.ts`, sharing its rule with the hook through `src/shared/reach.ts`). Prompts and subagents are always told; tool batches only when a peer joins, leaves or changes goal (tracked per subagent too), so a long turn hears about it without repeating itself. Hook bodies carry whole tool results, so the endpoint reads up to 64 MiB. A session alone, unframed or off the board hears only the docs section below; a tool batch with nothing new gets 204, which Claude Code treats as no output. Sessions started in a terminal carry no such hooks; adding the same `http` hooks to their settings opts them in.

Linked sessions and doc stores ride the same hook. Its answer gains a section naming every session linked to the caller (with why one can't be messaged: in the cloud, not running, or on another account) and asking it to work with them through SendMessage. A session listed as linked is left out of the frame-mates. Every caller, framed, linked or alone, also gets a docs section: the board keeps shared docs that sessions write for each other, the stores by title, id and file count (the first 15, then how many more), and a prompt to search and read what helps before and during the work, to write down what other sessions would benefit from (decisions, interfaces, how to run and test, gotchas, conventions, lessons) and to read a page again before changing it; with no stores yet it asks the session to start one when it has something worth passing on. Tool batches re-inject when a link is drawn or removed or the store list (ids and titles) changes, not on every file write, so a change reaches a running session on its next tool call.

Session MCP. Every session the board starts also gets `--mcp-config` with one stdio server, `kanban` (`src/agent/sessionMcp.ts`), never `--strict-mcp-config`, so the user's own servers stay; its settings pre-approve `mcp__kanban`. The process reads the session's own `CLAUDE_CODE_SESSION_ID` and the board's URL from its config `env`, since `--bg` hands the session to a worker that doesn't inherit the launcher's environment, and posts each call to `POST /api/docs/tools/<tool>` with the id in `x-kanban-session`. Every store is open to every session, with no links, joins or sharing (`src/agent/docTools.ts`, handled in `src/server/docsHttp.ts`): `list_doc_stores` lists each store's title, id, file count, last update and the first heading or line of its `index.md`; `search_docs` matches a query, case-insensitively, against store titles, paths and every text file of every store (or one), ranked by matches and capped at 40 lines, 3 per file; `list_docs`, `read_doc`, `write_doc`, `delete_doc` and `put_doc_asset` work on one store's files; and `create_doc_store`, `rename_doc_store` and `delete_doc_store` manage stores. Each tool's `store` is required and takes an id or an exact title, case-insensitive, and an ambiguous title is refused with the matching ids. `put_doc_asset` reads the image file in the MCP process and sends it as base64.

## Agent view

Opening a card shows the session's conversation drawn by the board itself, so it never depends on the size of the terminal the session runs in: a session in a quarter-width cmux pane still fills the window, and the whole history scrolls. The terminal (attach or mirror) stays one toggle away in the header.

`src/server/conversation.ts` folds transcript records into `ConversationItem`s (`src/shared/conversation.ts`): typed prompts with image counts, slash and `!` commands with their output, assistant text, thinking (Claude Code writes it redacted, so usually just its duration), tool calls paired with their results (text capped at 12k characters, errors, image counts, edit patches, a subagent's id, a question's answers), compaction boundaries with their summary, interruptions, notices (`informational`, `api_error`), peer messages, task notifications and prompts typed while the session was working (`queued_command` attachments from a person). Hook, prompt-snapshot, environment and other attachments are never sent to the page. A typed prompt whose parent record already has an earlier prompt (an Esc Esc rewind or an edit) replaces that earlier branch: its items become `rewound` and are not drawn, as the TUI shows only the active chain. A background launch (`async_launched` Workflow or Agent results, `backgroundTaskId` Bash results) carries its task id and stays running until a task notification names its tool use or task id, or TaskStop stops it. It also tracks the model, cwd, branch, permission mode (`permission-mode` records), context tokens (input plus cache plus output of the last reply), output tokens, when the current turn started and which tool calls have no result yet. Transcripts are read in chunks of at most 32 MiB and decoded one line at a time, and a single record over 64 MiB is skipped and counted rather than decoded (`src/server/ingest/lines.ts`), since decoding a huge transcript whole once crashed the board past V8's string limit; a log that still fails to read leaves the view and `answer_prompt` working from the screen. Each item has an index and a revision; a log keeps a random epoch so a reconnect with `since` gets only what changed, and a different epoch (the server restarted or the file was rewritten) gets a fresh window. The socket sends the newest 150 items, then changes as the file grows (polled every 400ms while someone watches); `more` pages 150 older ones, and the page loads them as you scroll up, keeping its place, with a Jump to latest pill while you are away from the bottom. Tool calls are compact lines that expand to their input and result: Bash shows the command, output and exit code, Edit, MultiEdit and Write a unified diff, Read the path and range, Grep and Glob the match count, Agent its prompt, result and a link to its subagent's view, with the subagent's own Working, Idle or Done badge in place of the call's mark once the board knows it, so a background launch that returned at once still reads as running or waiting like its card, TodoWrite a checklist, AskUserQuestion the answers, Artifact a link to the published page, MCP tools their input and result. A Workflow shows its summary and task id instead of its script, with the running and waiting counts of its run's agents on its line and each agent's badge and link in its body. A background Bash or Workflow keeps a running mark until its task notification. A call the user rejected is one short Rejected line instead of Claude Code's rejection text.

The status bar shows the turn's elapsed time while working, model, cwd, branch, permission mode (kept while a dialog hides the TUI's footer), how many tool calls are still running in the background, context and output tokens. The header's status line and the cards' status lines read markdown as plain text. Subagent cards open the same view, read-only, on the subagent's own transcript; so does any terminal session outside cmux.

Input goes through the drivers the board already has, and only for input: `cmux paste --submit` and forced `cmux send-key` for a session in a cmux pane (re-resolved every few seconds with the same live-process check as the mirror), and for a background session a `claude attach` pty at a fixed 120x40, opened only when something is sent or the session is waiting on a prompt, rendered by `@xterm/headless` so its screen can be read, and released after 30 idle seconds or when nobody watches. While the session's Terminal view is open, the attach hub keeps a headless copy of that attach's screen and the agent view types through it instead, so the session is never redrawn at 120x40 under someone's terminal; opening or closing the Terminal view releases the view's own attach. Input queued when the last viewer leaves is dropped, never typed. Every background session someone has open in the agent view counts as attached, whether or not its pty is open, so Butler's `send_prompt` leaves it alone. A live session with no transcript yet still opens, takes its first prompt, and picks the transcript up once it is written. The composer sends with Enter (Shift+Enter adds a line), recalls earlier prompts and commands with Up and Down at the edges, completes `/` commands and `@` files, interrupts with Esc or Stop, and cycles the permission mode with Shift+Tab, reading the mode back from the TUI's footer. Text typed while Claude works waits in the page's outbox, shown as queued, and goes out when the turn ends. Send now (Ctrl or ⌘+Enter in the composer, or Send now on a queued message) types it at once instead, ahead of anything else queued: Claude Code takes it mid-turn at its next step, so the page waits for the transcript to show a sent-now message until the turn has been over for a few seconds before calling it lost. An announcement (the megaphone in the top bar, or Butler's `announce` tool) types one message into every live session at once the same way, working or not, through the conversation hub's own driver, so sessions someone has open in the agent view are included; sessions waiting on a question or permission prompt, read-only ones and stopped or failed ones are skipped, `/`, `!` and `#` are refused, and each delivery is audited as `announce` with its length, never the text. Because a person is typing here, `/`, `!` and `#` are allowed; control characters (anything but newline and tab) and text over 16,000 characters are refused. Before every prompt and key the server reads the screen itself, not the board's lagging activity: nothing is typed while it shows a question, permission prompt or menu, and an attach send reads it again before pressing Enter. Esc is sent only while Claude works (the composer only sends it then) or to close a menu. A menu that is not a numbered prompt, such as Rewind, is recognised by its footer hint and shown as a dialog that names it, with Esc to close it and the terminal, so the composer can never type into it. A numbered list in the conversation above the TUI's input box is not mistaken for a prompt. The board agent's refusals in `prompts.ts` are unchanged. Every send is audited as `view-send` with its kind and length, never the text.

A session waits on a prompt when the board says it needs you and its transcript has a tool call without a result; a background job that is only blocked on its next instruction takes prompts. The server then reads the TUI's screen (cmux `read-screen`, or the headless attach) and offers a native form: AskUserQuestion with its options, descriptions, single or multiple choice and Other, from the tool's input; a permission prompt with the tool's input (the command, or the diff) and the TUI's own numbered choices as shown on screen. Answering drives the TUI with the keys it expects, worked out on Claude Code 2.1.292 against scratch sessions: the cursor moves with Up and Down (wrapping) and Enter picks; a multiple-choice row toggles with Enter and the Submit row moves on; Other is a row the answer is pasted into (forced, as the dialog refuses ordinary paste), which checks it; with more than one question a review step ends in Submit answers. Before every keystroke the server reads the screen and checks it shows the same question and choice, and after each move that the cursor landed; anything else stops with a message and leaves the prompt for the terminal. Success shows as the tool result arriving in the transcript. A permission answer is checked against a fresh screen, never a cached one: it must name the pending tool whose command (Bash) or file name (file tools) the prompt shows, so a repeated or late Yes cannot approve the next tool; while the prompt shows no pending tool's command it is not answerable. A prompt that is not a tool call shows the screen's own text above its choices. Wrapped choices in a narrow pane are joined, and choices clipped by a pane too small to list them all are marked, so the form offers the visible ones and says to widen the pane or use the terminal.

`@` completion lists the repository's tracked and untracked, not ignored, files (`git ls-files --cached --others --exclude-standard`), or walks the directory (skipping hidden directories and `node_modules`, 8 levels, 50,000 entries), cached for 10 seconds. It refuses a cwd inside `~/.claude`, through symlinks too, and drops any entry that resolves there, checked on the entries it returns. `/` completion reads only the first 4 KiB of each command or skill file for its name and description, and skips a project command or skill that resolves outside the project or into `~/.claude`.

Parity gaps: the panels that commands such as `/cost`, `/model` or `/config` open in the TUI are not drawn; the command runs and Esc closes the panel, but its content only shows in the terminal. Prompts that are not tool calls (folder trust, MCP approvals, plan approval) are offered only as a numbered list read from the screen, without context. Thinking text is redacted in current transcripts, so only its duration shows. Images are counted (as the TUI's [Image #N] placeholders), not shown as thumbnails: the page would need an endpoint serving image bytes out of transcripts, which is deferred. Text appears when Claude Code writes each message, not token by token. Prompt history is this session's own, not the TUI's history across sessions. Rewind, transcript mode and vim keys are not offered.

Known gaps after review, with reasons: hook output (stop_hook_summary, hook_success, hook_additional_context) and @-mention attachments (file reads, edited files, diagnostics) are still not drawn, since their shapes vary by hook and they are kept off the page with the other attachments; the TUI's background task list cannot stop a task from here, because stopping is a TaskStop the session itself must call; a foreground Agent call shows no live tool count or tokens, since its agent id arrives only with its result; teammates are not listed separately from subagents; workflow progress is shown as its agents' states, not the TUI's phase panel; a workflow agent with no card is labelled by its id; transcript updates still wait behind queued input, because ticks and input share one queue per session; Esc with queued prompts was not compared with the TUI; a menu opened from another terminal is only seen when the view reads the screen (while it sends or the session waits), though prompts are still refused against it; and the composer, question and permission forms on a cmux pane were exercised only through cmux's own refusals, since `cmux top` stopped listing processes during review. The guard for a permission prompt binds Bash and file tools by what the prompt shows; other tools are bound only by being the pending call.

## Ask Butler

Pressing / anywhere on the board pins a comment at the pointer and queues its text for Butler, the owner's assistant on spike, with what it was about: the session card or Butler card under the pin, the project region it sits in, and the part of the board on screen. The server never sends it anywhere; spike polls Butler's loopback endpoint every few seconds over ssh (`src/server/butlerInbox.ts`): `board_inbox` lists every queued message, `board_ack` moves the ones spike has safely stored into the thread's `waiting` list, which the page shows as Butler working, and `board_reply` appends his answer, or an error, to the thread and, for a message about a card, writes it into one Butler note beside that card, kept in `replyNote` and rewritten with each answer. Taking without acking leaves a message queued, so a crash on spike loses nothing. A thread is the whole conversation: replies go into the same Discord thread on spike. A session Butler starts with `start_session` while a message is waiting on him appears in the thread he took last, as a small live copy of its card that centres the real one on the board when pressed; `start_session` carries no thread, so with two messages open at once it picks the newer. Stopping a thread drops what was still queued and stops waiting for the rest. Spike counts as unreachable after 20 seconds without a poll, which the server broadcasts as `relay` in the `butler` frame.

Butler's Discord threads show as cards too (`src/server/butler.ts`, `src/server/butlerThreads.ts`). Spike sends the daemon's thread cards file with the Butler tool `butler_threads`: one card per thread active in the last day, id `thread-<Discord id>`, carrying the thread's kind (conversation, board, job, desk session, scheduled, voice), state, one-line status, Discord link and, for a thread another started, `parent`, the card id of the thread that started it. A new card goes beside its parent's card, else into a region named Butler, else somewhere clear, until the next tidy lays it out (see Tidy and the archive), and a card no longer listed goes to the archive and leaves with Butler's notes on it. Closing or deleting one keeps it off until its thread is active again, recorded as `dismissedThreads` in `butler.json`, and `put_card` never makes or rewrites one. A thread's events and the approvals waiting on the owner are kept apart from the cards, in `butler-threads.json`, and only `GET /api/butler/threads/<id>` serves them to the page; board_snapshot, board_history, the agent's tools, the audit and digests never see them. Clicking a thread card opens its log, what waits on the owner (answered in Discord), the changes, threads and sessions it started, and a reply box that posts to `POST /api/butler/threads/<id>/messages`, which queues the reply for spike like a / message, its `board_inbox` entry carrying `target`, the Discord thread to post it in, and its board thread `card-<id>`, whose `board_reply` goes into the card's log. The top bar's New Butler job starts a / thread at the middle of the screen through `POST /api/butler/jobs`, its message flagged `job`, which spike opens as a job thread. A change from `changes` with a `thread`, and a cloud session `start_session` was given a `parent`, link to that thread's card and show "from <thread>"; the thread card counts them as linked. A dashed Butler-coloured arrow runs from each thread card to every card and session it started, a desk session's thread from the thread that asked for it and its changes and sessions from it, so the whole family reads as one tree (`lineageEdges` in `src/web/butlerThreads.ts`). A thread card also carries its live `mission`, the mission's id and one line of what it covers, and the `machines` it drove, shown as chips on the card and kept off board_snapshot like its words. Each `butler_threads` reply ends with the orphan report: how many cloud sessions the board tracks, how many a Butler thread asked for, and why the rest have none (Butler's `start_session` without a parent, judged by its context pack in the prompt, a failover handover, or started on the board), and whether claude.ai answered the last poll.

Butler's DM with the owner is no card: it is his face over the board at every zoom, shown only while he is active (`src/web/ButlerDm.tsx`, its placement in `src/web/butlerDm.ts`). `butler_threads` keeps the DM's entry, the one of kind `dm`, as the board's DM state, takes any old DM card off without archiving it, and keeps its log like a card's under `thread-<id>`; the feed's Butler presence carries it as `dm`, its thread id, state, one-line status, link, how many approvals wait and when it was last active, plus the `mood` the daemon reads in Butler's latest reply (alarmed, amused, apologetic, concerned, content, curious, delighted, diligent, fixed, pondering, proud, puzzled or weary, anything else dropped), never its words. The face shows that mood's picture (`src/web/butler/moods`), or the bow-tie avatar without one, in a ring that is grey while idle, teal and gold while working, amber while something waits on the owner and red when failed, none of them animated, with the status beside it and a badge counting the approvals. It shows only when Butler does something: looks at or acts on the board, a DM reply arrives (its turn finishes or its mood changes), or something new waits on the owner, and hides 4 seconds after (`faceHoldMs`), staying while the pointer or focus is on it; a reload shows it only for board activity inside that hold. It moves as the old presence did: one 200ms ease-out snap to each spot, a single 160ms settle as it appears and a 100ms fade as its mood swaps, nothing looping, floating or bobbing (`faceMotion`, checked against `butlerDm.css` by its test). It sits at its spot and snaps beside whatever Butler is touching, never over a session, card, note or sticker, nor the top bar, rail, zoom controls or message button, and never off screen; dragged, it docks in a corner when dropped near one, or otherwise stays where it was dropped, remembered in the browser's local storage. While hidden it leaves a small, still face button in the board's bottom right, clear of the controls there, with an amber dot while something waits, which opens the DM, as does the B key anywhere on the board. The top bar's Board settings, kept per browser under `kanban.butlerFace`, choose Show only when active, the default, Always show or Never show, and Hide the Butler button. Under reduced motion it neither moves nor fades, and with a DM listed the board's own presence avatar is left out, keeping Butler's cursor and watching chips. Clicking it opens the DM's log like a thread card's, which closes on Escape or a click outside unless the owner pins it open beside the board with its pin, and its reply box queues the reply as `card-<id>` with the DM as `target`, which spike posts into the Discord DM, marked as sent from the board. A card or session the DM started, its parent the DM's `thread-<id>` or, while the board has no DM, a parent titled Direct messages with no card, shows a small "from DM" chip instead of a "from" link, which opens the DM, and no lineage arrow runs to it; such a card is laid out in the Butler region, and the archive names its parent DM.

Butler's message edges are drawn apart from his lineage arrows (`src/server/messageEdges.ts`, `src/web/butlerEdges.ts`): a thinner, finer-dotted Butler-coloured curve with no arrowhead, bending the other way to the session message arcs, from one end to the other, a thread card or a session card, with a pill at its middle saying how many messages went and when the last did, such as "3 · 4m ago". The DM has no card, so messages to or from it show instead as a dotted-bordered chip on the other end, "✉ 2 from DM · 5m", once the presence frame names the DM's thread. Clicking a pill or chip opens a small view listing those messages with their times, read from `GET /api/butler/edges?from=<end>&to=<end>`, each end `thread:<Discord id>` or `session:<id>`, which refuses a machine holding the runner token as the thread view does. The edges come from three places: `butler_threads`' top-level `edges`, the daemon's thread-to-thread messages such as a desk say, `{from, to, via, count, lastAt, messages}`, which replace the daemon's edges at each sync that carries them (a sync without `edges` leaves them be); `send_prompt` and `start_session` given a `parent`, each counted from that thread to the session as `prompt` or `start` with its text; and, on start, the board's audit log, whose `board-agent` entries record that `parent`, seeding any edge of the last day the store does not hold yet. Each edge keeps its last five messages, each cut to 600 characters, in `butler-edges.json`, and is forgotten a day after its last; the feed's `butler-edges` frame carries only `{from, to, via, count, lastAt}`, and board_snapshot, the agent's tools and digests never see the words.

The board agent, a headless Claude Code run the server once started for each comment, and its scheduled reports have been retired. Its comment threads load as read-only history (`to` absent); its top bar button results are dropped; `schedules.json` is renamed `schedules.json.retired` on the first start. `<state>/agent`, with its `.kanban-board-agent` marker, stays as the working directory of the board's own Claude runs, such as the digests, which ingest leaves off the board.

### Tidy and the archive

Butler's cards are laid out by construction (`src/server/tidy.ts`): each goes into one of four regions the board keeps by topic, Waiting on you for anything needing Aaron, Butler for conversations, board messages, desk sessions and what the DM started, Jobs for scheduled runs and jobs, and Changes for change cards, laid side by side from Waiting on you at the top left, a little left of the sessions, whose project regions stay as they are. The regions are found again by their folder under `/kanban/butler/`, which no session has, so a project region named after the `butler` repository is never mistaken for one. Inside each region the cards sit on a grid two slots wide, in a fixed order, state first (needing Aaron, working, failed, idle, done) and then newest first by when the work started, each card followed by the cards it started in the same region, with Butler's notes on a card in its slot beside it, so nothing overlaps; regions size to their cards, and a new card takes the next free slot. A card Aaron pinned (Pin in place, in its menu, which shows a pin on the card) or dragged in the last 10 minutes (the server records `movedAt` when the page moves one) stays where it is, and the grid flows around it. The pass runs 5 seconds after a `butler_threads` or `changes` sync that changed a card, from Butler's `tidy` tool, which spike's `kanban threads` runs every minute, and from the top bar's Tidy, which also forgets the spots of sessions nobody pinned, so the page lays them out afresh; Tidy is undoable and deletes nothing the archive does not keep.

The same pass archives finished work (`src/server/archive.ts`): a card whose state is done, a change finished or archived, a desk session or thread whose Discord thread was archived, a scheduled run done, goes to the archive 30 minutes after it finished, from the feed's `finishedAt` or else the time its timeline entered done, and at once when Aaron or Butler closes it. A card needing Aaron, working, idle, failed (until it is closed, which acknowledges it) or pinned never goes on its own. A board session goes to the archive once it has been gone from the board for 10 minutes. An archived thread or change stays off the board until it is active again, which takes it out of the archive. The daemon's feed and spike's change list send `startedAt`, `finishedAt` and `outcome` (done, failed or superseded) for each card, and a card closed before its work was done counts as superseded. Each entry keeps what it was (its kind: change, desk session, board session, scheduled job or conversation, and its task line), its project or Butler region, when it started and finished, who asked (its parent card), its outcome, its final report (a change's summary, a thread's last reply), its Discord and claude.ai links, the machines it drove, its mission, a thread's log, and the card itself to restore. It lives in `archive.json` in the board's state, written atomically like the rest, so backups of the state carry it; after 90 days an entry is compacted to its summary fields and at most 5000 are kept. Cards Aaron closed before the archive existed are backfilled from the daemon's entries of dismissed threads and from spike's records of closed changes as those syncs arrive. The sidebar's Archive lists them newest first, searchable and filterable by kind, project, outcome and date range, with a bar of how many finished each day; a row opens to its report, log and links read-only, and Restore to board puts a card back, pinned. Only the page reads it: `GET /api/archive` (`q`, `kind`, `project`, `outcome`, `from`, `to`) and `POST /api/archive/<id>/restore`, while board_snapshot, the agent's tools, the audit and digests never do; `POST /api/tidy` is the top bar's Tidy.

The safe set (`src/server/safePrompts.ts`, `safeVerdict`) decides which permission prompts `allow_safe` and `approve_safe_prompts` approve without Aaron. It judges a prompt by its tool name and by the label claude.ai shows for it, such as `Approve or deny claude-code-remote — Send Message` for `mcp__claude-code-remote__send_message`, through `promptTool`, which reads a tool from a label only for claude.ai's own server, `claude-code-remote` by its exact name, and only where the prompt gives the label as its name or the label agrees with a bare name, so a label never makes another tool look like one of the safe set's, and a label naming no server names no tool. It allows claude.ai's own session tools (`mcp__claude-code-remote__*`), the session's own housekeeping among them, its scheduled tasks (`create_trigger`, `update_trigger`, `delete_trigger`, `fire_trigger`), pull request subscriptions and webhooks (`watch_url`, `unwatch_url`), but those that change environments, credentials, computers, repository trust or another session's life, and a scheduled task naming a `persistent_session_id` or starting a new session on every firing; tools that only organise the session's own work or look something up (Workflow, Agent, Task and Todo tools, Skill, ToolSearch, WebFetch, WebSearch and the like); Read, Grep, Glob and LS of anything not secret-like; Edit, Write, MultiEdit and NotebookEdit of a path that is not secret-like (`.env*`, keys, `id_*`, credentials, secrets, `.ssh`, `.aws`, `.claude/settings*`, `.git` internals) and, when the board knows the session's folder, is inside it or a temp directory; the work review tooling's MCP tools and commands, named in `KANBAN_REVIEW_TOOLS` (comma-separated, kept in the board's environment rather than this public repository), but its merges, deploys, deletes and destroys; GitHub MCP reads, pull requests, comments and reviews, and branch writes off `main` and `master`. A Bash command is split into its simple commands, its `$(…)` and backtick substitutions included and heredoc bodies skipped as text, and every one must be a read, a build or test command of the repository, git work on a branch, a gh read, pull request, issue or comment, or a GET, or one of backlogic's runner commands: its cloud start-up entry, toolchain, heartbeat and hook dispatcher (`backlogic-cloud-*`), the repository's `bin/check` and `bin/wait-check`, sourcing `~/.backlogic-cloud`, `mise install`, and the `backlogic` CLI verbs a runner session uses on its own ticket, while its tokens, shares, users, grants, settings, runner controls and removals stay prompts. The guardrails stay prompts with their reason: pushing to `main` or `master`, the current branch unnamed, force pushes, deleting branches, tags or remote branches, `git clean`, merging a pull request, releases and non-GET API calls, deleting outside the folder, deploys and anything naming production, infrastructure and cluster changes, reading or printing secrets, sends, Slack posts and payments, `sudo` and other hosts, and the ways round them: variables such as `GIT_SSH_COMMAND`, `PAGER` or a relative `PATH` that make a later command run something else, git's `--upload-pack`, `--exec` and `--config-env`, sed's `e` and `w`, awk's pipes and `ENVIRON`, jq's `env`, a program from stdin or `-e`, a package npx would install that is not a known test tool, and task runner targets naming apply or destroy. An unknown tool or command, claude.ai's unknown session tools included, is never safe.

Approving a safe prompt of a cloud session answers it on claude.ai with `updatedPermissions` adding `SAFE_SESSION_RULES`, the input-free safe tools (never Read, Grep or Glob, whose secrets are judged each time, nor the scheduled task tools, which may reach a task that wakes another session, so each is judged and audited alone), as session rules (`decisionClassification` `user_permanent`), so a session already running stops asking for that whole set after its first safe prompt is approved; Bash and file edits keep being judged one prompt at a time. A cloud session can wait on several prompts at once, and every one is judged. A terminal session's safe prompt is answered with its Yes through the same path as `answer_prompt`. Each approval is audited as `prompt-approve` with the session, tool, request id and `via: "safe set"`.

Cloud sessions start with `--permission-mode auto`, or `KANBAN_CLOUD_PERMISSION_MODE`, since `--cloud` forwards no `bypassPermissions` and a session in the default mode asks for every MCP tool. Their mirror reads claude.ai's events a page at a time and appends them in batches of at most 500 events or about 8 MB, recording each batch as mirrored once it lands, so the whole history a restart rereads never becomes one string past V8's limit and a failed page resumes from the last batch written.

Security. `send_prompt` refuses a session waiting on a question or permission prompt (typing would answer it), a background session someone has open on the board, and a terminal session outside cmux, and it refuses text whose first non-space character is `!`, `/` or `#` (the session would run it as a shell command, slash command or memory note without asking) or that holds control characters (which could end the bracketed paste early and type the rest raw). Every tool call except the read-only snapshot, transcript and sticker search is audited as `board-agent` with the caller, its target, the text it sent, asked or started a session with, and its outcome; exits and new sessions are also audited as usual with identity `butler`.

`board_history` reads every Claude home's `jobs/*/state.json` updated since the window began, with the changes in each job's `timeline.jsonl` and its last message, and merges them with the board's sessions active in the window, ordered needs-you, failed, working, then the rest. For each distinct repository (a worktree path counts as its main checkout) it runs `git log origin/HEAD` (or `origin/main`, `origin/master`) since the window began. It answers in plain text of at most 36,000 characters, shared evenly between sessions after the commits, since Claude Code refuses MCP results much larger than that. Interactive sessions have no job, so one that ended during the window and left the board is missed.


## Accounts and failover

How a session gets its Claude account. A session the board starts on this machine runs `claude --bg` with the default login in `~/.claude` when no account is asked for, or `cswap run <n> --share-history -- claude --bg …` for another cswap account, which puts it in that account's profile, `<cswap root>/sessions/<n>-<email slug>/`, its `CLAUDE_CONFIG_DIR` for good. The new-session forms used to preselect the account the project's last session ran on (`lastRuns.json`), so a project kept starting on one account even after it filled. A cloud session takes the account asked for the same way, through that profile's login. A runner session runs `claude -p` on its machine's default login. `cswap auto` (a launchd agent on the work Mac) only switches which account `~/.claude` points at: a session already running in a profile stays on that profile's account, which is how ten sessions on one account all stopped together on 5 Nov 2026 with "You've hit your weekly limit" and a prompt sent to them got the same answer.

New sessions start on the best account (`src/shared/failover.ts`, `src/server/failover.ts`). With two or more cswap accounts, the board keeps the account asked for only while it can take a session, and otherwise picks the one with the most 5-hour and weekly headroom, the default on a tie, skipping an account at 98% of either window, one held out with `cswap disable` (`disabled` in `cswap list --json`), one whose plan blocks Claude Code, one whose usage is unknown, and one cooling down after a limit. The forms no longer preselect a last account that can't take one. The best account being the default login, the session runs on `~/.claude` as before. A runner with cswap on its machine (`--cswap`, `CSWAP_BIN`, default `cswap` on its PATH, `off` to turn it off) chooses the same way from its own `cswap list --json`.

A session that stopped on a limit moves. Every minute the board looks for sessions not working whose last line starts with Claude Code's limit message ("You've hit your weekly limit", "usage limit reached" and the like; a line that only mentions limits never counts). It cools that session's account until the reset of the window it filled, as cswap reports it, or an hour when cswap names none, then picks the best other account. A background session is stopped with `claude stop`, never removed, and continued in the background under the same id with `claude --bg --resume <id>` on the new account, with a short prompt telling it why and to carry on. A cloud session can't be resumed under another login, so the board starts a new cloud session on the new account with a handover prompt (its link, goal and last steps) and keeps the old one. Terminal sessions are left to their terminal. The runner does the same for its own sessions: a `claude -p` whose result is a limit message is resumed with `--resume <id>` on the next account, at most 4 times, its detail reading "Moved from ap2 to ap4 (limit)". The board moves one session at most once every 10 minutes and 4 times a day, so a bad account can't make it flap. Each move raises a board notification, "<name>: moved from ap2 to ap4 (limit)", opening the card, is audited as `failover-move` and listed under Moved off a limit in the Usage sidebar.

When every rotating account is at its limit the board raises one notification saying so and when the first frees up, shows the same as a banner in the Usage sidebar, and leaves the stopped sessions where they are, still resumable; once an account frees up, the next check moves them. There is no path from the board to Butler for alerts of its own (Butler reads Aaron's board messages, which only he writes), so the notification is the alert. `finish_session` can end a session stopped on a limit with `force`, since the readiness question runs on the same spent account, and a duplicate with `duplicateOf`; the exit stops and removes the background job, keeping its transcript.

The Usage sidebar lists, under each account, how many of the board's sessions run on it and which, opening their cards, and why failover is skipping it and until when, so a single point of failure shows before it fails.

## User flows

1. **Scan.** Open the board. Cards group into families (a session and everything it spawned), newest first by when they started, so cards stay put while sessions work. Each card shows its name and what it is doing above its goal in large type, with a state badge. Dragging a card carries everything linked to it: its subagents, the sessions it spawned or forked (unless they sit in another project) and the notes tethered to it. Linked cards kanban placed stay unpinned. A dragged card steps aside rather than land in another project's frame, and a drag that ends where it began moves nothing else. Every card, note, sticker, Butler card and project frame keeps at least one grid cell from the next, so nothing hugs or overlaps another, however it is placed: a card, note or project dragged too close stops at the nearest spot a cell clear, a resized card, note or region stops its edge a cell short, and a note, sticker or Butler card may sit inside a project's frame only clear of its edges and label bar. A region resized over a note or a card of its own directory may grow to hold it instead. Things already too close stay put until moved. Comment pins float over the board and are left out.
2. **Zoom for more or less.** The board keeps one layout at every zoom and changes what each place on it shows. Below 45% each project frame, and each card outside one, becomes a summary: the project, its sessions counted by state, the subagents not yet returned, the time its open tasks should all be done, a digest of what is being done across the project and how it is going, a line per session ordered needs-you first, with the question it asks, or why a working session looks stuck, and its task progress, and then a timeline. The summary scrolls when its frame is too small to show it all. Click the summary's title to zoom in on it, or a line to open that session. Subagent cards and their edges go; edges and messages between sessions stay. Between 45% and 120% the cards show as described above. From 120% to 600% a card becomes its own layout drawn at screen size, so zooming in gives it room rather than larger type, and one card can fill the screen. Its header holds the state badge, name, project, account, kind and age, the goal, the question when it needs you, and what it is doing; the label above the card folds into it. Below, in one column or two once the card is 760 screen pixels wide, come a Progress section, when its digest has arrived, saying what the session is doing, how far along it is and when the digest was made (it reads Stuck in amber, with the reason, only while the session is working and the digest saw it repeating a step, failing the same way or blocked on something it cannot fix), its task list (from TaskCreate and TaskUpdate, or TodoWrite) with a progress bar and the task in progress in bold, and a timeline of its tasks and its last 40 steps. The whole card scrolls inside its frame. Frame borders, ribbons, glows, region labels and subagent cards keep their size on screen too.

   A timeline scrolls sideways, opening on now, and reaches back at most three hours. A summary's timeline has a lane per session; a card's has one lane of tasks and one of steps, each step's text placed at its time and packed into rows so none overlap. Far out a step is a tick that names itself on hover. Finished tasks are green, the task in progress is in the accent colour and pending tasks are dashed. Each task runs from when it started, or when the one before it finished, to when it finished; the board records those times from TaskCreate, TaskUpdate and TodoWrite. While a session is working, watching or needs you, its task in progress is projected to take the session's typical task length, the average of its finished tasks, or the board's when it has finished none, and each pending task follows at that length; a task already running longer is projected to end now. The last projected end is the session's finish, shown as ~HH:MM, and the latest across a summary's sessions is the project's. With no finished task anywhere on the board there is no projection. Idle, done, failed and stopped sessions are never projected.

   A wheel over a summary, a card's body or a timeline that can scroll the way the wheel moves scrolls only that, and stops at its end rather than panning the board. A wheel gesture keeps doing what it started doing until the wheel rests for a quarter of a second, so a pan that slides a summary under the pointer keeps panning. Ctrl or ⌘ with the wheel, and a pinch, always zoom.
3. **Follow messages.** A message animates along a dashed arc from sender to recipient; the messages rail lists them newest first, and selecting one highlights both ends. Clicking an arc's count opens the messages it carries with their times; an arc a prompt or claude.ai's remote-session tools carried (`kind` `prompt` or `cloud`) is drawn in Butler's finer dots.
4. **Focus.** Click a card. It expands into the session's conversation with focus in the composer; type to send, and answer questions and permission prompts in place. Terminal in the header switches to the real TUI (an attach for a background session, the cmux mirror for a pane), Conversation switches back. Close returns to the board, and the session keeps running.
5. **Drive a cmux pane.** In the terminal view of a session in a cmux pane, a monospace mirror of the pane takes a prompt box (Enter sends, Shift+Enter adds a line; ↑, ↓ and Esc go straight through on an empty prompt) and buttons for the allowlisted keys. cmux refusals, such as a draft in the terminal's prompt, appear above the prompt.
6. **Read.** Any other interactive card (started in a terminal outside cmux), and every subagent card, opens its conversation read-only.
7. **Start.** New session: pick where it runs and a folder from the recent projects, or from Choose folder…, which browses that machine's own folders through `GET /api/folders`, so a runner's folders are listed by the runner and the hub's by the hub, optionally name it, give a first prompt. It appears on the board and opens focused. The folder is checked on the machine it will run on: the hub refuses a local one that isn't a folder on its disk with "<cwd> isn't a folder on <machine>, where the board runs. To start it on another machine, pick that machine under Where it runs.", naming "this Mac" when the hub is a Mac, and a runner refuses one it can't map with its own name in place of "this machine".

Pick a directory (recent ones suggested) and optionally a name. The region is a dashed frame that moves by dragging its label and resizes from any edge or corner, snapping to the grid. Sessions under its directory whose card centre lies inside belong to it, as do cards dropped there; the frame grows to hold them, always keeping one grid cell between its cards and its label bar, as it does at its sides and bottom, for every project frame, drawn or grouped, so a saved board's frames take the room on load with no card moved; and a project group touching it is adopted so one frame shows. Resizing starts from the region's drawn rectangle, not the frame grown around its cards, and an edge stops short of a neighbouring project. When a project's frame grows into another, as its cards gain subagents or new cards arrive, the other project steps right or down out of the way with its cards, notes and stickers, and so on down the board; the page does this shortly after the frames meet, never during a drag or while a quick prompt is open.

Right-clicking anywhere inside a drawn region opens the same menu topped with New session here, Add note here and Add sticker here. Escape or a click elsewhere closes it. Clicking a project's frame, or opening its menu, brings that frame in front of the frames it overlaps until another is brought forward, so a covered label or close button can be reached. A colour applies at once and sticks to the project's directory, so every frame for that cwd, drawn or grouped, shares it.

While any session needs you the tab's title reads "(N) kanban" and its icon wears an amber badge with the count. A session that starts needing you after the page loaded raises a banner under the top bar with its name and question (not the one you have open while looking at the page); clicking it opens the session, and it goes away when dismissed, opened or answered, three at a time with a count of the rest. A wheel over a note whose content overflows scrolls the note, not the board. Click selects, Shift+click adds to the selection, clicking the board clears it. Right-click a note or sticker for Edit text, Colour, Duplicate (⌘D), Bring to front (⌘]), Send to back (⌘[) and Delete (⌫); arrows nudge the selection a pixel, Shift+arrows a grid step. Notes and stickers sit above group frames and beneath cards (above the summaries when zoomed far out), in board coordinates, so they pan and zoom with everything else.

## Runners

The board runs sessions on the owner's other machines through `kanban-runner` (`src/runner/`), a small Node agent with no dependencies, bundled to `dist/runner.js`. The hub (`src/server/runners.ts`) keeps everything about runners in memory, like the rest of its view of sessions: a restart forgets them until their next heartbeat, a few seconds later.

Protocol, all JSON over HTTP with `Authorization: Bearer $KANBAN_RUNNER_TOKEN` (no Access, no Origin; anything else gets 401 or 403):
- `POST /api/runners/register` with a `RunnerReport` (`src/shared/runners.ts`): name, hostname, platform, boot time, cap, usage (cores, CPU busy share since the last report, load, memory total and used, disk total and free) and its sessions. Answers the runner's id (its name lower-cased to `a-z0-9-`), the heartbeat interval (5 s) and the poll wait (25 s). The name `local` is refused: it is the hub's own.
- `POST /api/runners/<id>/heartbeat` with the same report every 5 s. 404 means the hub restarted, so the runner registers again.
- `GET /api/runners/<id>/commands?wait=25000` is a long poll answering `{ commands }` as soon as there is one: `launch` (hub session id, folder, prompt, name and the hub's home directory), `stop` (session id, force) or `browse` (a path, absolute, starting with `~` or null, and the hub's home directory). Commands for a runner that hung up mid-poll go out on its next poll.
- `POST /api/runners/<id>/commands/<commandId>` answers a command with `{ ok }` or `{ ok: false, error }`, and a `browse` with `{ ok: true, listing }`. The hub waits 60 s for a launch or stop and 10 s for a browse, and refuses a listing that isn't well formed (a folder name with `/` or a control character, more than 1000 names) rather than pass it to the page.
- `POST /api/runners/docs/<tool>`, with the token, no `Origin` and the session's Claude id in `x-kanban-session`, runs one doc tool for a session on a runner, the same tools `POST /api/docs/tools/:tool` gives the board's own sessions on its loopback.
- `GET /api/runners`, with Access or the token, lists `RunnerView`s: the hub's own machine first, then the runners, online first.

The protocol is version 2 (`runnerProtocol`), reported in every `RunnerReport`; version 2 added `browse` (`browseProtocol`), so a runner reporting 1 is told to restart and fetch the board's current runner rather than sent one. A runner answers `browse` from `src/runner/browse.ts`, the same code the hub uses for its own disk: it lists only subfolders and links to them, never files, starts in `~/workspace` or the home folder, refuses relative paths, and maps a hub path through `--paths` and the home swap like a launch. Browsing changes nothing, so it owes no heartbeat. When a register is refused for its token, the hub notes the name it gave, only for a machine in `KANBAN_RUNNERS` it has never seen, so a stranger can't add rows; browsing that machine then says its token was refused, and one that never connected says to put the board's `KANBAN_RUNNER_TOKEN` in `~/.config/kanban/env` there and start `kanban-runner`.

Sessions on a runner share the board's doc stores like the board's own sessions (`src/runner/docsMcp.ts`): each gets `--mcp-config` with the `kanban` stdio server, pre-approved with `--allowedTools=mcp__kanban` since a headless session can't be asked, run as `runner.js --docs-mcp` from the same file, which reads the hub and token as the runner does, the token from the environment or `~/.config/kanban/env` and never from a command line, and posts each call to `POST /api/runners/docs/<tool>`. Before this a session placed on another machine had no docs at all, since the board's own server posts to its loopback.

A runner fetches `runner.js` from the hub only when it starts, so the registration answer also carries `runnerVersion`, the sha256 of the `runner.js` the hub's release serves, and every board release restarts the hub, so each runner registers again (`src/runner/update.ts`). A runner whose own file differs downloads `GET /runner.js` with its token once none of its sessions is starting or working, checks it hashes to that version, writes it over its own file and exits, and launchd or systemd starts it again on the new code. A download that fails or doesn't match is logged and not tried again until the hub announces another version, and a runner started from a checkout's source never updates itself.

A runner that misses heartbeats for 15 s is offline; nothing about it is an error. Boot time is reported rounded to the minute and survives sleep, so when a machine returns with the same boot time the gap was sleep; from then on its silences read "asleep", and a reboot resets that. Offline runners keep their last-known sessions on the board, shown idle with "<machine> is offline" as what they're doing, and refuse new ones.

A launch picks the runner from `runsOn` (`runner_<id>`), refuses it when the runner is offline, asleep, unknown or at its cap (live sessions plus launches in flight), and otherwise queues the command. The runner maps the folder (as is, `--paths` prefixes, then home directory swap), runs `claude -p --output-format stream-json --verbose` there with the prompt on stdin (so a Windows shell never sees it) plus the board's doc tools and any `KANBAN_RUNNER_CLAUDE_ARGS`, and reports the session as starting, working, done, failed or stopped, with its latest tool or line of text, its Claude session id and, on macOS and Linux, its CPU and memory from one `ps` call. The hub puts those sessions on the board under the hub's folder, so cards land in their project, with `runner: { id, name }`; they have no transcript or terminal on the hub yet. Exiting one sends `stop` (SIGTERM to the process group, SIGKILL after 10 s, or `taskkill /T /F` on Windows); exiting one that already ended takes it off the board. A runner keeps ended sessions for an hour, at most 20, and stops its sessions when it is stopped itself.

On the page (`src/web/Runners.tsx`, fed by a `runners` frame on the feed at most every 250 ms and every 5 s), the Usage sidebar gets a Runners section below the Claude usage: one row per machine with a status dot, its platform and "Online" or "Offline · seen 3m ago" (or "Asleep"), CPU, memory and disk bars on the same grid as the account rows, a Claude bar for sessions placed against the cap (amber when full) and the sessions placed there, each opening its card. Offline and asleep machines are dimmed. The Usage tab shows whenever there are runners, and its dot turns red while a machine that went offline (not to sleep) in the last hour is still gone. The "where it runs" picker lists each runner after the hub's own machine with its platform and load (`1/4`); one that is offline, asleep, unseen or full is shown but can't be picked, with the reason. Runner cards show a monitor icon titled "On <machine>".

The hub is a runner too, labelled "This Mac" when the board runs on a Mac and otherwise by its machine name (such as spike), since its disk is the board server's, not the browser's: it reports the same usage (`src/runner/usage.ts`) every 5 s, its cap from `KANBAN_RUNNER_CAP`, and the board's live local sessions as its allocation. Its cap is shown, not enforced, so local launches behave as before.

## Infrastructure

The host runs two launchd user agents, installed by `npm run launchd-setup` (`scripts/launchd-setup.ts`) from the main checkout, logging to `~/Library/Logs/kanban/`:
- `kanban`: plain `node src/server/main.ts` from the main checkout on `main`, with `~/.config/kanban/env` in its environment and a `PATH` that reaches `claude` (or `CLAUDE_BIN` set). KeepAlive.
- `kanban-tunnel`: `cloudflared tunnel run --token-file ~/.config/kanban/tunnel-token` for the `kanban` tunnel.

`app.js` and `app.css` keep fixed names, so they are served `no-cache` with an ETag and a rebuild shows on the next load; hashed files under `assets/` are cached as immutable.

A hostname such as `kanban.example.com` routes through the tunnel and is gated by Cloudflare Access on your Access team, allowing one identity. Defence in depth: cloudflared requires the Access token before proxying, the server verifies `Cf-Access-Jwt-Assertion` against the team's keys and audience, and WebSocket upgrades must come from the board's own origin.

The board can also listen on the WireGuard network (10.100.0.0/24): `KANBAN_HOST=127.0.0.1,10.100.0.11` binds both, one server behind both listeners (`src/server/listen.ts`), and a network address that isn't up yet (WireGuard still starting after boot or wake) is retried every 10 seconds instead of crashing the server. Loopback stays bound whatever is listed, so hooks, session tools and the tunnel keep working; the loopback-only endpoints (peer hook, session and board-agent tools) check the peer address, so they stay closed on the network listener. Machines authenticate there with the shared `KANBAN_RUNNER_TOKEN` as a bearer token (`runnerTokenCheck` in `src/server/auth.ts`, a SHA-256-then-`timingSafeEqual` compare); browsers keep using Access. `KANBAN_AUTH=off` is still refused when any listed address isn't loopback. The token lives only in `~/.config/kanban/env`: `launchd-setup` drops it from the plist environment and the server reads it from the file itself.

Development happens in worktrees or cloud clones with `KANBAN_AUTH=off`, which binds to localhost only, on another `KANBAN_PORT`; only the main checkout serves the live board. Changes reach it through `origin/main`: `npm run land` pushes. The owner's live board runs on spike, whose `kanban-update` builds `main` within a minute or two; the Mac's old `kanban-sync` updater is retired.

`scripts/cloudflare-setup.ts` creates the tunnel, its DNS record and the Access application from an API token and the account, zone, hostname, Access team and allowed email it is given, idempotently, and writes the tunnel token and audience to `~/.config/kanban/`.

A web app instead of a desktop wrapper: the server must run as a long-lived local service anyway, and a PWA manifest makes it installable.

## Visual design

Flat and quiet: a warm off-white canvas, white cards with hairline borders, no shadows except on the focused card, one accent colour. Inter for the interface, JetBrains Mono for terminals, Lucide icons. Light and dark follow the system, with a toggle. State is always colour plus shape.

Project regions are tinted from an eight-colour palette (`src/web/regions.css`, `src/shared/colours.ts`): a faint fill, a stronger border and a label chip whose text keeps at least 4.5:1 contrast in both themes. Each cwd hashes to a stable default colour, so a project keeps its colour everywhere, though two neighbours can share one; a chosen colour overrides it.
